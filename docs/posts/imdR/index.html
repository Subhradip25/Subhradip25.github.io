Scope and Audience

If you work on Indian climate science, whether in agricultural meteorology, hydrology, or environmental research, you almost certainly need long-term daily rainfall and temperature records. Getting those records, clipping them to your study area, and preparing them for statistical analysis has traditionally required downloading raw binary files from the IMD FTP server, writing custom parsers, and sourcing shapefiles independently. The imdR package handles all of that in a few lines of R.

This tutorial walks you through the entire workflow: installing the package, exploring administrative boundaries, downloading and extracting data for points and regions, exporting to CSV or spatial formats, computing standard climate indices, and testing for statistically significant trends using the Mann-Kendall method. No prior experience with imdR is assumed, though basic familiarity with R helps.

Workflow at a glance

Install imdR → explore administrative boundaries → download and extract data (point, district, state, bounding box) → export (CSV, NetCDF, GeoTIFF) → visualise → compute climate indices → perform Mann-Kendall trend analysis with Sen’s slope.

Background: How IMD Gridded Data Works

Before running any code, it helps to understand what the data actually are and how the package interacts with them. This section explains the structure of the gridded datasets and the aggregation rules you need to follow to get correct results.

From station observations to a regular grid

IMD maintains a network of rain-gauge and temperature stations across India. Each station records measurements at a single geographic point, so the raw data are spatially irregular: dense in some regions and sparse in others. That makes it difficult to answer area-based questions such as “how much rain fell over Karnal district last monsoon?”

To solve this, IMD applies spatial interpolation to convert the irregular station observations into a regular grid: a uniform lattice of cells that tiles the entire country. Each grid cell holds a single value for each day, representing the estimated average for that cell’s area. This is the same principle used by global reanalysis products such as ERA5 and CFSR.

The interpolation method IMD uses is inverse-distance weighted (IDW) interpolation. For each grid cell, the estimated value \(\hat{z}\) at location \((x, y)\) is:

\[\hat{z}(x, y) = \frac{\displaystyle\sum_{i=1}^{n} \frac{z_i}{d_i^p}}{\displaystyle\sum_{i=1}^{n} \frac{1}{d_i^p}}\]

where \(z_i\) is the observed value at station \(i\), \(d_i\) is the distance from that station to the grid cell centre, and \(p\) is the power parameter (typically \(p = 2\)). Stations closer to the cell centre receive higher weight; distant stations contribute less. The result is a spatially smooth, continuous surface that can be subset by any administrative or geographic boundary.

The three variables available through imdR differ in both spatial resolution and period of record:

Variable Resolution Grid size Available period Code
Rainfall 0.25° (approx. 28 km) 135 × 129 1901 to present rain
Maximum temperature 1.0° (approx. 111 km) 31 × 31 1951 to present tmax
Minimum temperature 1.0° (approx. 111 km) 31 × 31 1951 to present tmin
Differing periods of record

Rainfall data go back to 1901, but temperature records only start from 1951. If your analysis combines all three variables, the earliest possible start year is 1951. Requesting temperature before 1951 or rainfall before 1901 will return an error from the IMD server.

Spatial resolution matters for small regions

Rainfall is gridded at 0.25° (roughly 28 km per cell), while temperature uses a coarser 1.0° grid (roughly 111 km per cell). For a small district, there may be no temperature grid-cell centre falling within the boundary at all. The package provides a touches = TRUE argument to capture cells that merely overlap the boundary rather than requiring their centres to fall inside it. This is discussed in detail in Step 4.

Two rules for aggregating gridded data correctly

Getting regional summaries right requires following two simple but important principles.

Rule 1: Average across space. When you want a single value for a region on a given day, you take the mean of all grid cells within that region, not their sum. Each cell represents the same area, so summing them would multiply the value by the number of cells and give a physically meaningless result. The spatial mean is the correct areal estimate.

Mathematically, the areal mean \(\bar{z}\) for a region containing \(N\) grid cells on day \(t\) is:

\[\bar{z}_t = \frac{1}{N} \sum_{i=1}^{N} z_{i,t}\]

Rule 2: Sum rainfall over time; average temperature over time. Rainfall is a cumulative quantity. The total rainfall for a season or year is the sum of daily values. Temperature is not cumulative; the representative value for a period is always the mean of daily values.

For annual totals and means:

\[\text{Annual rainfall} = \sum_{t=1}^{365} \bar{z}_t \qquad \text{Annual mean temperature} = \frac{1}{365} \sum_{t=1}^{365} \bar{z}_t\]

These two rules apply throughout every step of this tutorial.

Installation

Prerequisites

You need two pieces of software before anything else:

  • R (the language): download from cran.r-project.org
  • RStudio Desktop (the interface): download from posit.co/download/rstudio-desktop

Install both with their default settings. Once installed, open RStudio. Everything from here on runs inside the RStudio console or an R script.

Installing imdR

You can install imdR from CRAN (the stable release, recommended for most users) or from GitHub (the development version, which may include new features not yet on CRAN). You only need to do this once.

From CRAN (stable, recommended):

install.packages("imdR")

This downloads the pre-compiled binary package from the CRAN mirror nearest to you and installs it. No additional tools are needed.

From GitHub (development version):

# remotes lets R install packages directly from GitHub
install.packages("remotes")
remotes::install_github("Subhradip25/imdR")

remotes::install_github() clones the repository, compiles the source code, and installs the package. On Windows this requires Rtools; see the note below.

Windows users: Rtools

If the GitHub installation asks for Rtools, download and install it from cran.r-project.org/bin/windows/Rtools, then re-run the remotes::install_github() line. The CRAN version does not require Rtools because it ships pre-compiled binaries.

Loading the package and setting your data directory

# Load imdR into your R session
library(imdR)

# Check which version you have installed
packageVersion("imdR")

# Define where downloaded data files will be saved.
# imdR never writes to a default location; you must always specify file_dir.
# On Windows, use forward slashes even though Windows usually uses backslashes.
file_dir <- "C:/Users/YourName/Documents/imdR_data"

# Create the folder if it does not exist yet
dir.create(file_dir, showWarnings = FALSE, recursive = TRUE)

The file_dir object is reused by every function in this tutorial. Setting it once here means you do not have to repeat the path in every call. The showWarnings = FALSE argument suppresses the warning that would appear if the folder already exists, and recursive = TRUE creates any parent folders that are missing.

Install once, load every session

install.packages() runs once and permanently adds the package to your R library. library(imdR) must be run at the start of every new R session to make the functions available. Think of installation as putting a book on your shelf and library() as opening it.

Administrative Boundaries

One of imdR’s most practical features is its bundled set of administrative boundaries. The package includes Survey of India (SOI) approved polygons for all 36 states and union territories of India and over 800 districts. You can extract data for any of these regions by name, without ever sourcing or loading a shapefile yourself.

# Print a data frame of all states and union territories
list_states()

# Print all districts within a given state
# Use the exact state name as it appears in list_states()
list_districts("Tripura")
list_districts("Haryana")

# Retrieve the boundary polygon for a region as an sf object
# This is useful if you want to inspect or plot the boundary
goa    <- get_boundary("state",    "Goa")
karnal <- get_boundary("district", "Karnal")

list_states() and list_districts() simply print the names recognised by the package. get_boundary() returns an sf polygon object, which you can pass to plot() or ggplot2 if you want to see the boundary before extracting data.

Exact spelling is required

All extraction functions match names exactly against the SOI nomenclature. If a name is not recognised, run list_districts("YourState") to find the correct spelling. Common sources of mismatch include prefixes like “North” or “West” and abbreviations (for example, “North Goa” not “N. Goa”).

Why bundled boundaries matter

Most gridded-data tools give you only the raw grid. To extract data for a specific region, you would normally have to find an appropriate shapefile, check that its coordinate reference system matches the grid, resolve any geometry errors, and write the clipping code yourself. By bundling validated, projection-matched boundaries, imdR reduces all of that to a single function call with a text argument. This is particularly valuable for district-level work, where publicly available shapefiles are often inconsistent in naming conventions across sources.

Point Extraction: Getting a Time Series for a Single Location

The most common starting point in climate analysis is extracting a daily time series for a specific location, such as a field station, a weather observatory, or a project site. You provide a latitude and longitude, specify the variable and year range, and imdR returns a tidy data frame with one row per day.

Extracting a single variable at a point

The example below downloads the maximum temperature record (1951 to 2025) for a location in Old Goa:

oldgoa_tmax <- get_point(
  lat      = 15.50,     # decimal degrees, WGS 84
  lon      = 73.91,
  variable = "tmax",    # "rain", "tmax", or "tmin"
  start_yr = 1951,
  end_yr   = 2025,
  file_dir = file_dir   # data files are cached here
)

# Preview the output
head(oldgoa_tmax)

# Quick summary
cat("Total rows:", nrow(oldgoa_tmax),
    "| Mean tmax:", round(mean(oldgoa_tmax$tmax, na.rm = TRUE), 1), "°C\n")

What this code does, step by step:

  1. get_point() checks whether the annual data files for the requested variable and year range already exist in file_dir. Any missing years are downloaded from the IMD server; years already cached are read from disk.
  2. For each day, the function identifies the nearest grid-cell centre to the supplied coordinates and extracts that cell’s value. This is the nearest-neighbour assignment: no interpolation is applied between cells.
  3. The function assembles a data frame with columns date, lat, lon, and the variable name (tmax in this case), and writes a CSV to file_dir automatically.
  4. The returned object is a standard R data frame. head() shows the first six rows; mean() with na.rm = TRUE computes the overall average ignoring any missing values.

For rainfall, you would substitute variable = "tmax" with variable = "rain" and set start_yr = 1901 to access the full 125-year record.

Expect the first download to be slow

get_point() fetches one file per year from the IMD server. Temperature files are roughly 1.3 MB each; rainfall files are roughly 25 MB each. Downloading the full 1901 to 2025 rainfall record therefore transfers around 1.6 GB of data. This first download is slow and depends on your internet connection. On all subsequent runs, the cached files are used and the function completes in seconds. If the server times out mid-download, simply re-run the same command: completed years are detected automatically and skipped.

Extracting all three variables at once

If you need rainfall, maximum temperature, minimum temperature, and the diurnal temperature range (DTR) together, get_point_all() retrieves all four in one call and merges them into a single data frame:

oldgoa_all <- get_point_all(
  lat      = 15.50,
  lon      = 73.91,
  start_yr = 1951,   # limited by temperature availability
  end_yr   = 2025,
  file_dir = file_dir
)

head(oldgoa_all)
# Columns: date, lat, lon, rain, tmax, tmin, dtr
# dtr = tmax - tmin (diurnal temperature range, in °C)

The diurnal temperature range (DTR) is computed internally as \(\text{DTR} = T_{max} - T_{min}\). It is a useful indicator of continentality and cloud cover: high DTR values suggest clear skies and dry conditions, while low DTR values often indicate cloudy, humid, or rainy periods.

Understanding what a “point” value represents

Your coordinates will rarely fall exactly on a grid-cell centre. get_point() assigns the value of the nearest cell centre to your location. For the rainfall grid (0.25° cells, roughly 28 km wide), the nearest cell is usually within 14 km of your location, which is a reasonable approximation for most purposes. For the temperature grid (1.0° cells, roughly 111 km wide), the nearest cell could be up to 55 km away and represents conditions over a much larger area. This is a fundamental property of the gridded data, not a limitation of the package. Temperature point values should therefore be interpreted as regional estimates rather than site-specific measurements.

Regional Extraction: States and Districts

In most research applications you want a daily time series that represents an entire administrative region rather than a single point. get_district_series() does this by identifying all grid cells whose centres fall within the region’s boundary, extracting their values for each day, and returning their spatial mean. This follows Rule 1 from the background section: aggregate across space by averaging, not summing.

Rainfall for an entire state

# Daily area-mean rainfall for Kerala, 1901 to 2025
kerala_rain <- get_district_series(
  variable = "rain",
  name     = "Kerala",
  start    = 1901,
  end      = 2025,
  level    = "state",    # "state" or "district"
  file_dir = file_dir
)

head(kerala_rain)

# Compute mean annual rainfall (Rule 2: sum daily rain, then average over years)
n_years <- length(unique(format(kerala_rain$date, "%Y")))
mean_annual_rain <- sum(kerala_rain$rain, na.rm = TRUE) / n_years
cat("Kerala mean annual rainfall:", round(mean_annual_rain, 1), "mm/year\n")

What this code does:

  1. get_district_series() retrieves the state boundary polygon for Kerala from the bundled shapefile.
  2. It identifies all rainfall grid-cell centres that fall within that polygon for each requested year.
  3. For each day, it computes the spatial mean across those cells: \(\bar{z}_t = \frac{1}{N}\sum_{i=1}^{N} z_{i,t}\).
  4. It returns a data frame with columns date, region, and rain, and saves a CSV in file_dir.
  5. To get mean annual rainfall, we sum all daily values (Rule 2: rainfall accumulates) and divide by the number of years. The format(kerala_rain$date, "%Y") call extracts the four-digit year from each date string, and unique() gives us the count of distinct years.

Rainfall for a district

# Daily area-mean rainfall for Karnal district, 1901 to 2025
karnal_rain <- get_district_series(
  variable = "rain",
  name     = "Karnal",
  start    = 1901,
  end      = 2025,
  level    = "district",
  file_dir = file_dir
)

head(karnal_rain)

The code is identical to the state-level call except that level = "district". The function automatically looks up the Karnal district polygon and clips the national rainfall grid to it.

Small districts and the coarse temperature grid

A district smaller than a 1.0° temperature cell may contain no grid-cell centre within its boundary. In that case get_district_series() returns all-NA values for temperature. The solution is touches = TRUE, which captures any cell that the boundary touches or overlaps, even if its centre lies outside:

goa_tmax <- get_district_series(
  variable = "tmax",
  name     = "Goa",
  start    = 1951,
  end      = 2025,
  level    = "state",
  file_dir = file_dir,
  touches  = TRUE       # include cells overlapping the boundary
)

This is the recommended default for all temperature extractions over small regions.

Combining all three variables for a district

Many agricultural and agrometeorology applications need rainfall, maximum temperature, and minimum temperature in a single tidy table. Because temperature constrains the period, the record starts in 1951:

# Download each variable separately, suppressing individual CSVs
kr <- get_district_series("rain", "Karnal", 1951, 2025,
                          file_dir = file_dir, save_csv = FALSE)
kx <- get_district_series("tmax", "Karnal", 1951, 2025,
                          file_dir = file_dir, save_csv = FALSE, touches = TRUE)
kn <- get_district_series("tmin", "Karnal", 1951, 2025,
                          file_dir = file_dir, save_csv = FALSE, touches = TRUE)

# Merge the three data frames on the date and region columns
karnal_all <- Reduce(
  function(a, b) merge(a, b, by = c("date", "region")),
  list(kr, kx, kn)
)

# Compute diurnal temperature range and sort by date
karnal_all$dtr <- round(karnal_all$tmax - karnal_all$tmin, 3)
karnal_all     <- karnal_all[order(karnal_all$date), ]

# Save as a single merged CSV
write.csv(karnal_all,
          file.path(file_dir, "karnal_all_vars_1951_2025.csv"),
          row.names = FALSE)

head(karnal_all)

What Reduce() does here: Reduce() applies a two-argument function (merge) repeatedly across a list of data frames, merging them pairwise. With three data frames kr, kx, and kn, it first merges kr and kx on date and region, then merges that result with kn. The final output has one row per day with all four variables. Setting save_csv = FALSE on each get_district_series() call suppresses the three separate output files so that only your merged file is written to disk.

Why suppress individual CSVs?

By default, get_district_series() writes a separate CSV for each variable. If you intend to merge them anyway, setting save_csv = FALSE keeps your file_dir tidy and avoids three partially redundant files alongside your merged output.

Spatial Export: NetCDF and GeoTIFF

A collapsed time series (one value per day for a region) is ideal for statistical analysis, but some workflows require the full gridded surface for a region. For instance, you might want to visualise spatial rainfall patterns within a state in QGIS, or supply a 3-D array (latitude × longitude × time) to a Python-based crop model. The extract_by_boundary() function handles this by masking the national grid to your region and writing the result to a file.

Choosing the right output format

Three formats are supported, each suited to different downstream tools:

NetCDF (.nc) stores the complete latitude × longitude × time data array together with coordinate metadata and variable attributes in a single self-describing file. It is the standard format in climate science and is readable by R (terra, ncdf4), Python (xarray, netCDF4), CDO, and NCO. Choose NetCDF when you need to do further analysis programmatically.

GeoTIFF (.tif) stores raster data with spatial reference information embedded, with each day as a separate band. It is the standard format for GIS software (QGIS, ArcGIS) and is suitable when your primary goal is mapping or spatial overlay. Choose GeoTIFF when your downstream tool is a GIS.

CSV stores a long-format table with one row per cell per day, with columns for date, latitude, longitude, and value. File size grows rapidly for multi-year, multi-cell exports (a state over many decades can run to hundreds of megabytes or more), but CSV is convenient for spreadsheet and tidyverse workflows.

Exporting a state to NetCDF, year by year

# Step 1: download all years as a named list of SpatRaster objects
rain_long <- get_data("rain", 1901, 2025, file_dir)

# Step 2: loop over years and clip each raster to Kerala's boundary
for (yr in names(rain_long)) {
  extract_by_boundary(
    rain_long[[yr]],
    level    = "state",
    name     = "Kerala",
    variable = "rain",
    save     = TRUE,
    format   = "netcdf",
    file_dir = file_dir
  )
}

Why loop year by year? get_data() returns a named list where each element is a SpatRaster object for one year, with daily layers (365 or 366 depending on leap years). Loading all years into memory at once would create a stack of over 45,000 layers, which would overwhelm RAM for most computers. Processing one year at a time keeps memory usage low and produces one NetCDF file per year, which is a common and manageable archive structure.

Exporting all three variables for a district

for (v in c("rain", "tmax", "tmin")) {
  # Use 1951 as the start year for all variables so the archive is consistent
  vg <- get_data(v, 1951, 2025, file_dir)

  for (yr in names(vg)) {
    extract_by_boundary(
      vg[[yr]],
      level    = "district",
      name     = "Dhalai",
      variable = v,
      save     = TRUE,
      format   = "netcdf",
      file_dir = file_dir
    )
  }
}

The outer loop iterates over variable names; the inner loop iterates over years. The result is a set of NetCDF files organised by variable and year in file_dir.

Exporting a single year as GeoTIFF

rain2020 <- get_data("rain", 2020, 2020, file_dir)

extract_by_boundary(
  rain2020,
  level    = "district",
  name     = "North Goa",
  variable = "rain",
  save     = TRUE,
  format   = "geotiff",
  file_dir = file_dir
)

This produces a multi-band GeoTIFF with 366 bands (2020 was a leap year), one per day. Open it in QGIS and use the band selector to navigate through the monsoon season.

Custom Regions: The Bounding Box

Administrative boundaries do not always match ecological or hydrological study areas. If your region of interest is defined by coordinates rather than by a state or district name, use get_bbox(). You specify the latitude and longitude limits of a rectangle, and the function extracts everything within that box.

Typical use cases include the Indo-Gangetic Plains, the Western Ghats, a river basin extent, or a rectangular domain for a regional climate model.

# Western Ghats bounding box, single year, saved as NetCDF
wghats_nc <- get_bbox(
  lat_min  = 8,   lat_max = 21,
  lon_min  = 73,  lon_max = 78,
  variable = "rain",
  start_yr = 2020,
  end_yr   = 2020,
  file_dir = file_dir,
  format   = "netcdf"
)

# Same region, same year, saved as GeoTIFF instead
wghats_tif <- get_bbox(
  lat_min  = 8,   lat_max = 21,
  lon_min  = 73,  lon_max = 78,
  variable = "rain",
  start_yr = 2020,
  end_yr   = 2020,
  file_dir = file_dir,
  format   = "geotiff"
)

For long-term bounding-box archives, iterate over years to keep memory manageable:

# Download 125 years of rainfall for the Indo-Gangetic Plains
for (yr in 1901:2025) {
  get_bbox(
    lat_min  = 24,  lat_max = 30,
    lon_min  = 73,  lon_max = 88,
    variable = "rain",
    start_yr = yr,
    end_yr   = yr,
    file_dir = file_dir,
    format   = "netcdf"
  )
}

Each iteration of the loop downloads and saves one year’s worth of data. If the loop is interrupted (for example, by a server timeout), you can restart it: years already saved to file_dir are detected and skipped automatically.

Automatic clipping at the data boundary

get_bbox() clips the requested rectangle to the spatial extent of the IMD dataset. If your coordinates extend beyond the coverage area (for example, into the ocean or into neighbouring countries), a warning is issued and the box is trimmed to the valid region automatically. No data are returned for areas outside IMD coverage.

Mapping a Single Day

Before moving to time series analysis, it is useful to look at the spatial pattern of a variable on a specific day. plot_imd() produces a ready-to-use map with administrative boundaries overlaid, for the whole of India or a specific region.

# Load the 2020 rainfall raster (already cached from earlier steps)
rain2020 <- get_data("rain", 2020, 2020, file_dir)

# Map rainfall across all of India on 28 June 2020
plot_imd(rain2020, "2020-06-28", "rain")

# Zoom in to Kerala
plot_imd(rain2020, "2020-06-28", "rain",
         level = "state", name = "Kerala")

# Zoom in to a district
plot_imd(rain2020, "2020-06-28", "rain",
         level = "district", name = "North Goa")

The date argument accepts the format "YYYY-MM-DD". The function selects the corresponding layer from the multi-layer SpatRaster object, clips it to the specified region, and draws the map with boundary overlays. 28 June 2020 is used here because it falls during the active southwest monsoon season, so the spatial contrast between the wet west coast and the drier interior is clearly visible.

Saving maps for publication

Add save_path = file.path(file_dir, "kerala_rain_20200628.png") to the plot_imd() call to write a 300-dpi PNG file suitable for journal figures. The file is saved to the path you specify.

Long-Term Trend Plots

A time series of daily values spanning several decades produces a graph that is too dense to read. For long-term analysis, the standard approach is to aggregate daily data to one value per year and plot that annual series. This transforms tens of thousands of data points into a manageable sequence of 75 to 125 values that clearly shows multi-decadal patterns.

Annual aggregation: applying the two rules

Following Rule 2 from the background section, rainfall is aggregated by summing daily values within each calendar year to get the annual total (mm/year). Temperature is aggregated by averaging daily values within each year to get the annual mean (°C).

\[\text{Annual total rainfall in year } y = \sum_{t \in y} \bar{z}_t\]

\[\text{Annual mean temperature in year } y = \frac{1}{|y|} \sum_{t \in y} \bar{z}_t\]

where \(|y|\) is the number of days in year \(y\) (365 or 366). Plotting these annual values reveals multi-decadal trends, periodic signals like ENSO, and interannual variability that is completely invisible in daily data.

Annual rainfall trend plot

library(ggplot2)

# Use the Karnal district series downloaded in Step 4
# Extract the four-digit year from each date
karnal_rain$year <- as.integer(format(karnal_rain$date, "%Y"))

# Sum daily rainfall within each year (Rule 2: rainfall accumulates)
annual_rain <- aggregate(rain ~ year, karnal_rain, sum)

ggplot(annual_rain, aes(x = year, y = rain)) +
  geom_col(fill = "#2E86C1", alpha = 0.85) +          # annual bars
  geom_smooth(method = "lm", se = FALSE,
              color = "#C0392B", linewidth = 1) +      # linear trend line
  labs(
    title = "Karnal: Annual Total Rainfall (1901 to 2025)",
    x     = "Year",
    y     = "Rainfall (mm/year)"
  ) +
  theme_bw(base_size = 13)

Reading the code: format(karnal_rain$date, "%Y") converts each date to a four-digit year string; as.integer() makes it numeric so ggplot2 treats it as a continuous variable. aggregate(rain ~ year, karnal_rain, sum) groups the data frame by year and applies sum() to the rain column, producing one row per year. geom_col() draws the bars; geom_smooth(method = "lm") overlays an ordinary least-squares regression line to show the long-term direction of change.

Annual temperature trend plot

# Temperature record starts in 1951
karnal_tmax <- get_district_series("tmax", "Karnal", 1951, 2025,
                                   file_dir = file_dir, touches = TRUE)

karnal_tmax$year <- as.integer(format(karnal_tmax$date, "%Y"))

# Average daily tmax within each year (Rule 2: temperature does not accumulate)
annual_tmax <- aggregate(tmax ~ year, karnal_tmax, mean)

ggplot(annual_tmax, aes(x = year, y = tmax)) +
  geom_line(color = "#C0392B", linewidth = 0.8) +

The dashed trend line fitted by geom_smooth(method = "lm") tells you whether values are generally going up or down, but it does not tell you whether the trend is statistically significant. A visually obvious upward slope might still fail a significance test if the year-to-year variability is very high. Step 10 covers the proper statistical test for trend significance.

Climate Indices

Annual totals and means summarise the quantity of a climate variable but say nothing about its distribution within the year. Two districts might have identical annual rainfall totals but very different rainfall regimes: one might receive its rain in many moderate events spread through the year, while the other receives the same total in a few intense bursts separated by long dry spells. These differences have large consequences for agriculture, water resources, and flood risk.

Climate indices are designed to capture these characteristics. Each index reduces the daily record to a single value per year that describes a specific aspect of the distribution, such as the number of rainy days, the length of the longest dry spell, or the intensity of the heaviest events.

Why indices matter more than totals

Consider two districts, A and B, each receiving 800 mm of annual rainfall. District A receives it over 120 rainy days; District B receives it over 30 days. For agriculture, these are completely different climates. In District A, the risk of prolonged moisture stress is low. In District B, even though the total is the same, crops face extended dry periods between infrequent heavy rains, and the risk of flash flooding during rain events is much higher.

The WMO/ETCCDI (Expert Team on Climate Change Detection and Indices) has defined a standard suite of daily climate indices specifically to document these differences and track how they change over time. imdR implements the most widely used subset of these indices for both rainfall and temperature.

Trend Analysis: Mann-Kendall Test and Sen's Slope

Once you have an annual series, whether a raw total, a mean, or a climate index, the natural next question is: is there a statistically significant long-term trend? This section explains why ordinary regression is not the best tool for climate data and how the Mann-Kendall test and Sen’s slope together provide a more appropriate analysis.

Why not just use linear regression?

Ordinary least-squares (OLS) linear regression fits a line by minimising the sum of squared residuals. It has several assumptions that climate data frequently violate:

  1. Normality: OLS assumes residuals are normally distributed. Rainfall series are often right-skewed because of years with extreme events.
  2. Homoscedasticity: OLS assumes constant variance. Climate variability often increases in wetter years.
  3. Sensitivity to outliers: One extremely wet or dry year can substantially change the slope estimate.

The Mann-Kendall test avoids all three problems because it is non-parametric: it makes no assumptions about the distribution of the data. Instead of fitting a line, it counts the number of concordant pairs (pairs where the later value is larger than the earlier) minus the number of discordant pairs (pairs where the later value is smaller). The test statistic \(S\) is:

\[S = \sum_{i=1}^{n-1} \sum_{j=i+1}^{n} \text{sgn}(x_j - x_i)\]

where \(\text{sgn}(\cdot)\) is the sign function: +1 if positive, 0 if zero, -1 if negative. Under the null hypothesis of no trend, \(S\) follows an approximately normal distribution for \(n > 10\). The standardised statistic is:

\[Z = \begin{cases} \dfrac{S - 1}{\sqrt{\text{Var}(S)}} & \text{if } S > 0 \\ 0 & \text{if } S = 0 \\ \dfrac{S + 1}{\sqrt{\text{Var}(S)}} & \text{if } S < 0 \end{cases}\]

Kendall’s \(\tau\) (tau), also reported, is a normalised version of \(S\) in the range \([-1, 1]\): \(\tau = S / \binom{n}{2}\). Values near +1 indicate a strong increasing trend; values near -1 indicate a strong decreasing trend.

Sen’s slope estimates the magnitude of change. It is the median of all pairwise slopes:

\[\hat{\beta} = \text{median}\left(\frac{x_j - x_i}{j - i}\right) \quad \text{for all } j > i\]

Because it uses the median rather than the mean, Sen’s slope is resistant to the influence of single extreme years. The units are “change per year” (for example, mm/year for rainfall or °C/year for temperature).

Output column What it tells you
tau Direction and strength of the trend, ranging from -1 (consistently decreasing) to +1 (consistently increasing)
pvalue Probability of observing a trend this strong by chance if there were no real trend; smaller is stronger evidence
sens_slope Estimated rate of change per year in the original units of the variable

Testing trends in climate indices

The most informative application of trend analysis is not the annual total but the indices. It is entirely possible for annual rainfall to be stationary while the character of that rainfall changes: fewer rainy days, higher intensity, longer dry spells. Detecting this requires testing each index independently:

# karnal_idx was computed in Step 9 and has one row per year

# Is annual total rainfall changing?
trend_analysis(karnal_idx, index_col = "total",
               name = "Karnal", file_dir = file_dir)

# Are the number of rainy days changing?
trend_analysis(karnal_idx, index_col = "dr",
               name = "Karnal", file_dir = file_dir)

# Are very heavy rainfall events becoming more frequent?
trend_analysis(karnal_idx, index_col = "d115",
               name = "Karnal", file_dir = file_dir)

# Is the longest dry spell within each year getting longer?
trend_analysis(karnal_idx, index_col = "cdd",
               name = "Karnal", file_dir = file_dir)

Each call produces an independent test for that index. You can run as many as you need; just keep in mind that testing many indices simultaneously increases the chance of a false positive, so consider applying a Bonferroni correction to your significance threshold if you are reporting results formally.

Reading the significance notation

Results are reported using standard notation: *** for p ≤ 0.001, ** for p ≤ 0.01, * for p ≤ 0.05, . for p ≤ 0.10, and ns for not significant. A result labelled ns does not prove there is no trend; it means the available data do not provide sufficient evidence to reject the null hypothesis of no trend. With a short record (say, 30 to 40 years), even a real trend may not reach significance because the test has low statistical power.

Minimum record length for meaningful trend analysis

The Mann-Kendall test is mathematically valid with as few as three observations, but trend results are only scientifically meaningful over extended periods. The World Meteorological Organization recommends a minimum of 30 years for climate normals, and this is a reasonable minimum for trend analysis too. Over short records, even strong visual patterns in a plot may not be statistically distinguishable from noise. Where possible, use the full available record (1901 to 2025 for rainfall, 1951 to 2025 for temperature) to maximise statistical power.

Putting It All Together: A Complete Research Example

To see how the individual steps combine, consider this research question: Is monsoon rainfall in Karnal becoming more intense and erratic over time, even if the annual total has not changed significantly?

Here is the complete analytical pipeline:

Step 1: Acquire the data.

karnal_rain <- get_district_series("rain", "Karnal", 1901, 2025, file_dir = file_dir)

Step 2: Compute climate indices.

                                       name = "Karnal", file_dir = file_dir)

Step 3: Test three indices.

trend_analysis(karnal_idx, "dr",    "Karnal", file_dir)   # Are rainy days declining?
trend_analysis(karnal_idx, "d115",  "Karnal", file_dir)   # Are extreme events increasing?
trend_analysis(karnal_idx, "cdd",   "Karnal", file_dir)   # Are dry spells getting longer?

Step 4: Interpret the combination. If the annual total shows ns (no significant trend) but the number of rainy days shows a significant decreasing trend while very-heavy-rainfall days show a significant increasing trend, your conclusion is clear: the same quantity of rain is arriving in fewer, more intense events. This is a well-documented signal of changing rainfall regimes across South Asia and constitutes a publishable finding supported by 125 years of daily data.

## Background: How IMD Gridded Data Works

Before running any code, it helps to understand what the data actually are and how the package interacts with them. This section explains the structure of the gridded datasets and the aggregation rules you need to follow to get correct results.

::: {.imd-concept}
#### From station observations to a regular grid

IMD maintains a network of rain-gauge and temperature stations across India. Each station records measurements at a single geographic point, so the raw data are spatially irregular: dense in some regions and sparse in others. That makes it difficult to answer area-based questions such as "how much rain fell over Karnal district last monsoon?"

To solve this, IMD applies spatial interpolation to convert the irregular station observations into a **regular grid**: a uniform lattice of cells that tiles the entire country. Each grid cell holds a single value for each day, representing the estimated average for that cell's area. This is the same principle used by global reanalysis products such as ERA5 and CFSR.

The interpolation method IMD uses is inverse-distance weighted (IDW) interpolation. For each grid cell, the estimated value $\hat{z}$ at location $(x, y)$ is:

$$\hat{z}(x, y) = \frac{\displaystyle\sum_{i=1}^{n} \frac{z_i}{d_i^p}}{\displaystyle\sum_{i=1}^{n} \frac{1}{d_i^p}}$$

where $z_i$ is the observed value at station $i$, $d_i$ is the distance from that station to the grid cell centre, and $p$ is the power parameter (typically $p = 2$). Stations closer to the cell centre receive higher weight; distant stations contribute less. The result is a spatially smooth, continuous surface that can be subset by any administrative or geographic boundary.
:::

::: {.imd-card .warn}
<div class="imd-card-title">Spatial resolution matters for small regions</div>

Rainfall is gridded at 0.25° (roughly 28 km per cell), while temperature uses a coarser 1.0° grid (roughly 111 km per cell). For a small district, there may be no temperature grid-cell centre falling within the boundary at all. The package provides a `touches = TRUE` argument to capture cells that merely overlap the boundary rather than requiring their centres to fall inside it. This is discussed in detail in Step 4.
:::

::: {.imd-concept}
#### Two rules for aggregating gridded data correctly

Getting regional summaries right requires following two simple but important principles.

**Rule 1: Average across space.** When you want a single value for a region on a given day, you take the **mean** of all grid cells within that region, not their sum. Each cell represents the same area, so summing them would multiply the value by the number of cells and give a physically meaningless result. The spatial mean is the correct areal estimate.

Mathematically, the areal mean $\bar{z}$ for a region containing $N$ grid cells on day $t$ is:

$$\bar{z}_t = \frac{1}{N} \sum_{i=1}^{N} z_{i,t}$$

**Rule 2: Sum rainfall over time; average temperature over time.** Rainfall is a cumulative quantity. The total rainfall for a season or year is the **sum** of daily values. Temperature is not cumulative; the representative value for a period is always the **mean** of daily values.

For annual totals and means:

$$\text{Annual rainfall} = \sum_{t=1}^{365} \bar{z}_t \qquad \text{Annual mean temperature} = \frac{1}{365} \sum_{t=1}^{365} \bar{z}_t$$

These two rules apply throughout every step of this tutorial.
:::

You provide a latitude and longitude, specify the variable and year range, and `imdR` returns a tidy data frame with one row per day.

### Extracting a single variable at a point

The example below downloads the maximum temperature record (1951 to 2025) for a location in Old Goa:

```{r}
#| label: point-single
#| eval: false
oldgoa_tmax <- get_point(
  lat      = 15.50,     # decimal degrees, WGS 84
  lon      = 73.91,
  variable = "tmax",    # "rain", "tmax", or "tmin"
  start_yr = 1951,
  end_yr   = 2025,
  file_dir = file_dir   # data files are cached here
)

# Preview the output
head(oldgoa_tmax)

# Quick summary
cat("Total rows:", nrow(oldgoa_tmax),
    "| Mean tmax:", round(mean(oldgoa_tmax$tmax, na.rm = TRUE), 1), "°C\n")
```

**What this code does, step by step:**

1. `get_point()` checks whether the annual data files for the requested variable and year range already exist in `file_dir`. Any missing years are downloaded from the IMD server; years already cached are read from disk.
2. For each day, the function identifies the nearest grid-cell centre to the supplied coordinates and extracts that cell's value. This is the nearest-neighbour assignment: no interpolation is applied between cells.
3. The function assembles a data frame with columns `date`, `lat`, `lon`, and the variable name (`tmax` in this case), and writes a CSV to `file_dir` automatically.
4. The returned object is a standard R data frame. `head()` shows the first six rows; `mean()` with `na.rm = TRUE` computes the overall average ignoring any missing values.

For rainfall, you would substitute `variable = "tmax"` with `variable = "rain"` and set `start_yr = 1901` to access the full 125-year record.

::: {.imd-card .warn}
<div class="imd-card-title">Expect the first download to be slow</div>

`get_point()` fetches one file per year from the IMD server. Temperature files are roughly 1.3 MB each; rainfall files are roughly 25 MB each. Downloading the full 1901 to 2025 rainfall record therefore transfers around 1.6 GB of data. This first download is slow and depends on your internet connection. On all subsequent runs, the cached files are used and the function completes in seconds. If the server times out mid-download, simply re-run the same command: completed years are detected automatically and skipped.
:::

### Extracting all three variables at once

If you need rainfall, maximum temperature, minimum temperature, and the diurnal temperature range (DTR) together, `get_point_all()` retrieves all four in one call and merges them into a single data frame:

```{r}
#| label: point-all
#| eval: false
oldgoa_all <- get_point_all(
  lat      = 15.50,
  lon      = 73.91,
  start_yr = 1951,   # limited by temperature availability
  end_yr   = 2025,
  file_dir = file_dir
)

head(oldgoa_all)
# Columns: date, lat, lon, rain, tmax, tmin, dtr
# dtr = tmax - tmin (diurnal temperature range, in °C)
```

The diurnal temperature range (DTR) is computed internally as $\text{DTR} = T_{max} - T_{min}$. It is a useful indicator of continentality and cloud cover: high DTR values suggest clear skies and dry conditions, while low DTR values often indicate cloudy, humid, or rainy periods.

::: {.imd-concept}
#### Understanding what a "point" value represents

Your coordinates will rarely fall exactly on a grid-cell centre. `get_point()` assigns the value of the **nearest** cell centre to your location. For the rainfall grid (0.25° cells, roughly 28 km wide), the nearest cell is usually within 14 km of your location, which is a reasonable approximation for most purposes. For the temperature grid (1.0° cells, roughly 111 km wide), the nearest cell could be up to 55 km away and represents conditions over a much larger area. This is a fundamental property of the gridded data, not a limitation of the package. Temperature point values should therefore be interpreted as regional estimates rather than site-specific measurements.
:::

```{=html}
<div class="imd-step"><span class="imd-step-num">4</span><h2>Regional Extraction: States and Districts</h2></div>
```

In most research applications you want a daily time series that represents an entire administrative region rather than a single point. `get_district_series()` does this by identifying all grid cells whose centres fall within the region's boundary, extracting their values for each day, and returning their spatial mean. This follows Rule 1 from the background section: aggregate across space by averaging, not summing.

### Rainfall for an entire state

```{r}
#| label: state-series
#| eval: false
# Daily area-mean rainfall for Kerala, 1901 to 2025
kerala_rain <- get_district_series(
  variable = "rain",
  name     = "Kerala",
  start    = 1901,
  end      = 2025,
  level    = "state",    # "state" or "district"
  file_dir = file_dir
)

head(kerala_rain)

# Compute mean annual rainfall (Rule 2: sum daily rain, then average over years)
n_years <- length(unique(format(kerala_rain$date, "%Y")))
mean_annual_rain <- sum(kerala_rain$rain, na.rm = TRUE) / n_years
cat("Kerala mean annual rainfall:", round(mean_annual_rain, 1), "mm/year\n")
```

**What this code does:**

1. `get_district_series()` retrieves the state boundary polygon for Kerala from the bundled shapefile.
2. It identifies all rainfall grid-cell centres that fall within that polygon for each requested year.
3. For each day, it computes the spatial mean across those cells: $\bar{z}_t = \frac{1}{N}\sum_{i=1}^{N} z_{i,t}$.
4. It returns a data frame with columns `date`, `region`, and `rain`, and saves a CSV in `file_dir`.
5. To get mean annual rainfall, we sum all daily values (Rule 2: rainfall accumulates) and divide by the number of years. The `format(kerala_rain$date, "%Y")` call extracts the four-digit year from each date string, and `unique()` gives us the count of distinct years.

```{r}
head(karnal_rain)
```

The code is identical to the state-level call except that `level = "district"`. The function automatically looks up the Karnal district polygon and clips the national rainfall grid to it.

::: {.imd-card .warn}
<div class="imd-card-title">Small districts and the coarse temperature grid</div>

The solution is `touches = TRUE`, which captures any cell that the boundary *touches or overlaps*, even if its centre lies outside:


:::

### Combining all three variables for a district

Many agricultural and agrometeorology applications need rainfall, maximum temperature, and minimum temperature in a single tidy table. Because temperature constrains the period, the record starts in 1951:

```{r}
#| label: district-all
#| eval: false
# Download each variable separately, suppressing individual CSVs
kr <- get_district_series("rain", "Karnal", 1951, 2025,
                          file_dir = file_dir, save_csv = FALSE)
kx <- get_district_series("tmax", "Karnal", 1951, 2025,
                          file_dir = file_dir, save_csv = FALSE, touches = TRUE)
kn <- get_district_series("tmin", "Karnal", 1951, 2025,
                          file_dir = file_dir, save_csv = FALSE, touches = TRUE)

# Merge the three data frames on the date and region columns
karnal_all <- Reduce(
  function(a, b) merge(a, b, by = c("date", "region")),
  list(kr, kx, kn)
)

# Compute diurnal temperature range and sort by date
karnal_all$dtr <- round(karnal_all$tmax - karnal_all$tmin, 3)
karnal_all     <- karnal_all[order(karnal_all$date), ]

# Save as a single merged CSV
write.csv(karnal_all,
          file.path(file_dir, "karnal_all_vars_1951_2025.csv"),
          row.names = FALSE)

head(karnal_all)
```

**What `Reduce()` does here:** `Reduce()` applies a two-argument function (`merge`) repeatedly across a list of data frames, merging them pairwise. With three data frames `kr`, `kx`, and `kn`, it first merges `kr` and `kx` on `date` and `region`, then merges that result with `kn`. The final output has one row per day with all four variables. Setting `save_csv = FALSE` on each `get_district_series()` call suppresses the three separate output files so that only your merged file is written to disk.

::: {.imd-card .tip}
<div class="imd-card-title">Why suppress individual CSVs?</div>

By default, `get_district_series()` writes a separate CSV for each variable. If you intend to merge them anyway, setting `save_csv = FALSE` keeps your `file_dir` tidy and avoids three partially redundant files alongside your merged output.
:::

```{=html}
<div class="imd-step"><span class="imd-step-num">5</span><h2>Spatial Export: NetCDF and GeoTIFF</h2></div>
```

A collapsed time series (one value per day for a region) is ideal for statistical analysis, but some workflows require the full gridded surface for a region. For instance, you might want to visualise spatial rainfall patterns within a state in QGIS, or supply a 3-D array (latitude × longitude × time) to a Python-based crop model. The `extract_by_boundary()` function handles this by masking the national grid to your region and writing the result to a file.

::: {.imd-concept}
#### Choosing the right output format

Three formats are supported, each suited to different downstream tools:

**NetCDF (.nc)** stores the complete latitude × longitude × time data array together with coordinate metadata and variable attributes in a single self-describing file. It is the standard format in climate science and is readable by R (`terra`, `ncdf4`), Python (`xarray`, `netCDF4`), CDO, and NCO. Choose NetCDF when you need to do further analysis programmatically.

**GeoTIFF (.tif)** stores raster data with spatial reference information embedded, with each day as a separate band. It is the standard format for GIS software (QGIS, ArcGIS) and is suitable when your primary goal is mapping or spatial overlay. Choose GeoTIFF when your downstream tool is a GIS.

**CSV** stores a long-format table with one row per cell per day, with columns for date, latitude, longitude, and value. File size grows rapidly for multi-year, multi-cell exports (a state over many decades can run to hundreds of megabytes or more), but CSV is convenient for spreadsheet and tidyverse workflows.
:::

### Exporting a state to NetCDF, year by year

```{r}
#| label: state-netcdf
#| eval: false
# Step 1: download all years as a named list of SpatRaster objects
rain_long <- get_data("rain", 1901, 2025, file_dir)

# Step 2: loop over years and clip each raster to Kerala's boundary
for (yr in names(rain_long)) {
  extract_by_boundary(
    rain_long[[yr]],
    level    = "state",
    name     = "Kerala",
    variable = "rain",
    save     = TRUE,
    format   = "netcdf",
    file_dir = file_dir
  )
}
```

**Why loop year by year?** `get_data()` returns a named list where each element is a `SpatRaster` object for one year, with daily layers (365 or 366 depending on leap years). Loading all years into memory at once would create a stack of over 45,000 layers, which would overwhelm RAM for most computers. Processing one year at a time keeps memory usage low and produces one NetCDF file per year, which is a common and manageable archive structure.

The outer loop iterates over variable names; the inner loop iterates over years. The result is a set of NetCDF files organised by variable and year in `file_dir`.

```{=html}
<div class="imd-step"><span class="imd-step-num">8</span><h2>Long-Term Trend Plots</h2></div>
```

A time series of daily values spanning several decades produces a graph that is too dense to read. For long-term analysis, the standard approach is to aggregate daily data to one value per year and plot that annual series. This transforms tens of thousands of data points into a manageable sequence of 75 to 125 values that clearly shows multi-decadal patterns.

::: {.imd-concept}
#### Annual aggregation: applying the two rules

Following Rule 2 from the background section, rainfall is aggregated by **summing** daily values within each calendar year to get the annual total (mm/year). Temperature is aggregated by **averaging** daily values within each year to get the annual mean (°C).

$$\text{Annual total rainfall in year } y = \sum_{t \in y} \bar{z}_t$$

$$\text{Annual mean temperature in year } y = \frac{1}{|y|} \sum_{t \in y} \bar{z}_t$$

where $|y|$ is the number of days in year $y$ (365 or 366). Plotting these annual values reveals multi-decadal trends, periodic signals like ENSO, and interannual variability that is completely invisible in daily data.
:::

### Annual rainfall trend plot

```{r}
#| label: annual-trend-rain
#| eval: false
library(ggplot2)

# Use the Karnal district series downloaded in Step 4
# Extract the four-digit year from each date
karnal_rain$year <- as.integer(format(karnal_rain$date, "%Y"))

# Sum daily rainfall within each year (Rule 2: rainfall accumulates)
annual_rain <- aggregate(rain ~ year, karnal_rain, sum)

ggplot(annual_rain, aes(x = year, y = rain)) +
  geom_col(fill = "#2E86C1", alpha = 0.85) +          # annual bars
  geom_smooth(method = "lm", se = FALSE,
              color = "#C0392B", linewidth = 1) +      # linear trend line
  labs(
    title = "Karnal: Annual Total Rainfall (1901 to 2025)",
    x     = "Year",
    y     = "Rainfall (mm/year)"
  ) +
  theme_bw(base_size = 13)
```

**Reading the code:** `format(karnal_rain$date, "%Y")` converts each date to a four-digit year string; `as.integer()` makes it numeric so ggplot2 treats it as a continuous variable. `aggregate(rain ~ year, karnal_rain, sum)` groups the data frame by year and applies `sum()` to the `rain` column, producing one row per year. `geom_col()` draws the bars; `geom_smooth(method = "lm")` overlays an ordinary least-squares regression line to show the long-term direction of change.

### Annual temperature trend plot

```{r}
#| label: annual-trend-temp
#| eval: false
# Temperature record starts in 1951
karnal_tmax <- get_district_series("tmax", "Karnal", 1951, 2025,
                                   file_dir = file_dir, touches = TRUE)

karnal_tmax$year <- as.integer(format(karnal_tmax$date, "%Y"))

# Average daily tmax within each year (Rule 2: temperature does not accumulate)

```

A line-and-point style (`geom_line` + `geom_point`) is conventional for temperature series because temperature is a continuous quantity without natural breaks between years, unlike rainfall totals which are conceptually discrete annual sums.

::: {.imd-card .tip}
<div class="imd-card-title">The regression line shows direction, not significance</div>

The dashed trend line fitted by `geom_smooth(method = "lm")` tells you whether values are generally going up or down, but it does not tell you whether the trend is statistically significant. A visually obvious upward slope might still fail a significance test if the year-to-year variability is very high. Step 10 covers the proper statistical test for trend significance.
:::

```{=html}
<div class="imd-step"><span class="imd-step-num">9</span><h2>Climate Indices</h2></div>
```

Annual totals and means summarise the quantity of a climate variable but say nothing about its distribution within the year. Two districts might have identical annual rainfall totals but very different rainfall regimes: one might receive its rain in many moderate events spread through the year, while the other receives the same total in a few intense bursts separated by long dry spells. These differences have large consequences for agriculture, water resources, and flood risk.

Climate indices are designed to capture these characteristics. Each index reduces the daily record to a single value per year that describes a specific aspect of the distribution, such as the number of rainy days, the length of the longest dry spell, or the intensity of the heaviest events.

::: {.imd-concept}
#### Why indices matter more than totals

Consider two districts, A and B, each receiving 800 mm of annual rainfall. District A receives it over 120 rainy days; District B receives it over 30 days. For agriculture, these are completely different climates. In District A, the risk of prolonged moisture stress is low. In District B, even though the total is the same, crops face extended dry periods between infrequent heavy rains, and the risk of flash flooding during rain events is much higher.

The WMO/ETCCDI (Expert Team on Climate Change Detection and Indices) has defined a standard suite of daily climate indices specifically to document these differences and track how they change over time. `imdR` implements the most widely used subset of these indices for both rainfall and temperature.
:::

### Rainfall indices

```{r}
#| label: rain-indices
#| eval: false
# Load the full rainfall grid as a list of annual SpatRasters
rain_long <- get_data("rain", 1901, 2025, file_dir)

# Compute standard annual rainfall indices for Karnal district
# Returns one row per year with all index values
karnal_idx <- compute_rainfall_indices(
  rain_long,
  level    = "district",
  name     = "Karnal",
  file_dir = file_dir
)

head(karnal_idx)
```

`compute_rainfall_indices()` loops over each year's raster, clips it to the Karnal boundary, and computes the spatial mean for each day before calculating the indices from that daily mean series. The output data frame has one row per year. The indices returned are:

The PCI is worth explaining in a little more detail. It measures how evenly rainfall is distributed across the months of the year. A value near 8.3 (the theoretical minimum for 12 equal months) means rainfall is uniformly spread through the year. Higher values indicate increasing concentration into fewer months, which is characteristic of strongly monsoonal climates. Values above 20 indicate a highly seasonal distribution.

### Temperature indices

```{r}
#| label: temp-indices
#| eval: false
# Load the temperature grids
tmax_long <- get_data("tmax", 1951, 2025, file_dir)
tmin_long <- get_data("tmin", 1951, 2025, file_dir)

# Compute annual temperature indices for Goa state
# Both tmax and tmin grids are required simultaneously
temp_idx <- compute_temp_indices(
  tmax_long,
  tmin_long,
  level    = "state",
  name     = "Goa",
  file_dir = file_dir
)

```

The function requires both `tmax` and `tmin` grids because some indices (such as DTR and tropical nights) combine both. The output includes:

- **TXx / TNn**: hottest day of the year ($\max T_{max}$) and coldest night ($\min T_{min}$)
- **SU35**: number of summer days where $T_{max} \geq 35$ °C (heat stress threshold for most crops)
- **TR25**: number of tropical nights where $T_{min} \geq 25$ °C (relevant for human thermal comfort)
- **WSDI / CSDI**: warm-spell and cold-spell duration indices, defined as the number of days in runs of at least 6 consecutive days above the 90th or below the 10th percentile of daily temperature

These correspond to the standard ETCCDI temperature indicators used in IPCC assessment reports and national climate change assessments.

```{=html}
<div class="imd-step"><span class="imd-step-num">10</span><h2>Trend Analysis: Mann-Kendall Test and Sen's Slope</h2></div>
```

Once you have an annual series, whether a raw total, a mean, or a climate index, the natural next question is: is there a statistically significant long-term trend? This section explains why ordinary regression is not the best tool for climate data and how the Mann-Kendall test and Sen's slope together provide a more appropriate analysis.

::: {.imd-concept}
#### Why not just use linear regression?

Ordinary least-squares (OLS) linear regression fits a line by minimising the sum of squared residuals. It has several assumptions that climate data frequently violate:

1. **Normality**: OLS assumes residuals are normally distributed. Rainfall series are often right-skewed because of years with extreme events.
2. **Homoscedasticity**: OLS assumes constant variance. Climate variability often increases in wetter years.
3. **Sensitivity to outliers**: One extremely wet or dry year can substantially change the slope estimate.

The **Mann-Kendall test** avoids all three problems because it is non-parametric: it makes no assumptions about the distribution of the data. Instead of fitting a line, it counts the number of concordant pairs (pairs where the later value is larger than the earlier) minus the number of discordant pairs (pairs where the later value is smaller). The test statistic $S$ is:

$$S = \sum_{i=1}^{n-1} \sum_{j=i+1}^{n} \text{sgn}(x_j - x_i)$$

where $\text{sgn}(\cdot)$ is the sign function: +1 if positive, 0 if zero, -1 if negative. Under the null hypothesis of no trend, $S$ follows an approximately normal distribution for $n > 10$. The standardised statistic is:

$$Z = \begin{cases} \dfrac{S - 1}{\sqrt{\text{Var}(S)}} & \text{if } S > 0 \\ 0 & \text{if } S = 0 \\ \dfrac{S + 1}{\sqrt{\text{Var}(S)}} & \text{if } S < 0 \end{cases}$$

Kendall's $\tau$ (tau), also reported, is a normalised version of $S$ in the range $[-1, 1]$: $\tau = S / \binom{n}{2}$. Values near +1 indicate a strong increasing trend; values near -1 indicate a strong decreasing trend.

**Sen's slope** estimates the magnitude of change. It is the median of all pairwise slopes:

$$\hat{\beta} = \text{median}\left(\frac{x_j - x_i}{j - i}\right) \quad \text{for all } j > i$$

Because it uses the median rather than the mean, Sen's slope is resistant to the influence of single extreme years. The units are "change per year" (for example, mm/year for rainfall or °C/year for temperature).
:::

```{r}
  index_col = "rain",
  name      = "Karnal",
  file_dir  = file_dir
```

`trend_analysis()` prints the Mann-Kendall statistics to the console, writes a CSV of the results to `file_dir`, and produces a plot of the annual series with the Sen's slope line superimposed. The Sen's slope line is more appropriate than an OLS line for this plot because it is not distorted by extreme years.

### Testing trends in climate indices

The most informative application of trend analysis is not the annual total but the indices. It is entirely possible for annual rainfall to be stationary while the *character* of that rainfall changes: fewer rainy days, higher intensity, longer dry spells. Detecting this requires testing each index independently:

```{r}
#| label: trend-indices
#| eval: false
# karnal_idx was computed in Step 9 and has one row per year

# Is annual total rainfall changing?
trend_analysis(karnal_idx, index_col = "total",
               name = "Karnal", file_dir = file_dir)

# Are the number of rainy days changing?
trend_analysis(karnal_idx, index_col = "dr",
               name = "Karnal", file_dir = file_dir)

# Are very heavy rainfall events becoming more frequent?
trend_analysis(karnal_idx, index_col = "d115",
               name = "Karnal", file_dir = file_dir)

# Is the longest dry spell within each year getting longer?
trend_analysis(karnal_idx, index_col = "cdd",
               name = "Karnal", file_dir = file_dir)
```

Each call produces an independent test for that index. You can run as many as you need; just keep in mind that testing many indices simultaneously increases the chance of a false positive, so consider applying a Bonferroni correction to your significance threshold if you are reporting results formally.

::: {.imd-card .tip}
<div class="imd-card-title">Reading the significance notation</div>

Results are reported using standard notation: `***` for p ≤ 0.001, `**` for p ≤ 0.01, `*` for p ≤ 0.05, `.` for p ≤ 0.10, and `ns` for not significant. A result labelled `ns` does not prove there is no trend; it means the available data do not provide sufficient evidence to reject the null hypothesis of no trend. With a short record (say, 30 to 40 years), even a real trend may not reach significance because the test has low statistical power.
:::

::: {.imd-card .warn}
<div class="imd-card-title">Minimum record length for meaningful trend analysis</div>

The Mann-Kendall test is mathematically valid with as few as three observations, but trend results are only scientifically meaningful over extended periods. The World Meteorological Organization recommends a minimum of 30 years for climate normals, and this is a reasonable minimum for trend analysis too. Over short records, even strong visual patterns in a plot may not be statistically distinguishable from noise. Where possible, use the full available record (1901 to 2025 for rainfall, 1951 to 2025 for temperature) to maximise statistical power.
:::

## Putting It All Together: A Complete Research Example

To see how the individual steps combine, consider this research question: **Is monsoon rainfall in Karnal becoming more intense and erratic over time, even if the annual total has not changed significantly?**

::: {.imd-concept}
Here is the complete analytical pipeline:

**Step 1: Acquire the data.**
```r
karnal_rain <- get_district_series("rain", "Karnal", 1901, 2025, file_dir = file_dir)
```

**Step 2: Compute climate indices.**
```r
rain_long  <- get_data("rain", 1901, 2025, file_dir)
karnal_idx <- compute_rainfall_indices(rain_long, level = "district",
                                       name = "Karnal", file_dir = file_dir)
```

**Step 3: Test three indices.**
```r
trend_analysis(karnal_idx, "total", "Karnal", file_dir)   # Is the total changing?
trend_analysis(karnal_idx, "dr",    "Karnal", file_dir)   # Are rainy days declining?
trend_analysis(karnal_idx, "d115",  "Karnal", file_dir)   # Are extreme events increasing?
trend_analysis(karnal_idx, "cdd",   "Karnal", file_dir)   # Are dry spells getting longer?
```

**Step 4: Interpret the combination.**
If the annual total shows `ns` (no significant trend) but the number of rainy days shows a significant *decreasing* trend while very-heavy-rainfall days show a significant *increasing* trend, your conclusion is clear: the same quantity of rain is arriving in fewer, more intense events. This is a well-documented signal of changing rainfall regimes across South Asia and constitutes a publishable finding supported by 125 years of daily data.
:::
